# 📝 US-051: El Operario Dado de Alta Recibe un Código con el que Realmente Puede Entrar

> **Navegación del Framework SDD:**
> [⬅️ US-010](./US-010.md) | [📖 Índice de Historias de Usuario](../indice_user_stories.md) | [🧪 AUDIT-DEV-017](../../../audits/AUDIT-DEV-017-rbac-matrix-and-operator-identity.md)

---

## 🗣️ Narrativa (Comportamiento y Negocio)

**Como** Administrador del restaurante (Rol: `ADMIN`),
**Cuando** doy de alta a un operario nuevo desde Gestión de Personal,
**Quiero** asignarle yo mismo un código de operario corto y memorizable, verlo después en la lista de personal, y que ese código sea exactamente lo que el operario teclea en la terminal táctil,
**Para** poder entregarle unas credenciales utilizables en el momento, sin consultar la base de datos ni pedirle que teclee un identificador de 36 caracteres.

---

## 🚦 Precondiciones

- El administrador está autenticado con permiso `users:manage`.
- El operario aún no existe; su código no está en uso por ningún otro operario, activo o bloqueado.

---

## 🧪 Criterios de Aceptación (BDD Gherkin)

@critical @smoke
### Escenario 1: Alta con código y login inmediato (Happy Path — cierra `US-010` Escenario 1)
*   **Given** que un Administrador abre «Alta de Operario»
*   **When** registra a `"Carlos Gómez"` con código `"CG-01"`, rol `KITCHEN_STAFF` y PIN `"4321"`
*   **Then** el sistema crea la cuenta con estado `ACTIVE` y retorna `HTTP 201 Created`
*   **And** la confirmación en pantalla muestra el código `"CG-01"` de forma destacada, no solo el nombre
*   **And** el operario inicia sesión inmediatamente tecleando `"CG-01"` y su PIN, sin que nadie consulte la base de datos.

@critical
### Escenario 2: El código es visible en la lista de personal
*   **Given** que existen operarios registrados
*   **When** el Administrador abre «Bloquear / Reactivar»
*   **Then** cada fila muestra el código de operario junto al nombre, el rol y el estado
*   **And** el Administrador puede leérselo a un operario que lo ha olvidado, sin acceso técnico al sistema.

@critical
### Escenario 3: La unicidad la impone la base de datos (Guard 39)
*   **Given** que ya existe un operario con código `"CG-01"`
*   **When** el Administrador intenta dar de alta a otro con el mismo código
*   **Then** el sistema rechaza la operación con `HTTP 409 Conflict` y un cuerpo RFC 7807 que nombra el código en conflicto
*   **And** el rechazo procede de la restricción única real de la base de datos, no de una comprobación previa en código — dos altas simultáneas con el mismo código no pueden crear ambas la fila.

@edge
### Escenario 4: Formato y normalización del código (QA Edge Case Senior)
*   **Given** que el Administrador teclea el código con minúsculas y espacios sobrantes (`"  cg-01  "`)
*   **When** envía el alta
*   **Then** el sistema normaliza a `"CG-01"` antes de persistir, de modo que el operario puede teclearlo en cualquier caja
*   **And** un código vacío, más largo de 12 caracteres o con caracteres fuera de `A-Z`, `0-9` y `-` se rechaza con `HTTP 400` y mensaje explícito
*   **And** el login es insensible a mayúsculas y a espacios por el mismo motivo ergonómico.

@edge
### Escenario 5: Los usuarios preexistentes conservan su acceso
*   **Given** un despliegue cuya base de datos ya tiene usuarios creados antes de esta historia
*   **When** se aplica la migración
*   **Then** cada usuario existente recibe como código su identificador actual, de forma que **ninguna credencial en circulación deja de funcionar**
*   **And** `bootstrap-admin` conserva literalmente `bootstrap-admin` como código, manteniendo válidas las credenciales de revisión publicadas.

---

## 🔒 Criterios de Aceptación No Funcionales (NFRs)

*   **Ergonomía Táctil (hereda de `US-001`):** el código debe poder teclearse con guantes en una terminal táctil — máximo 12 caracteres, alfabeto sin ambigüedad visual entre mayúsculas y minúsculas.
*   **No divulgación:** ninguna superficie **sin autenticar** lista operarios ni códigos. El código se teclea; nunca se ofrece en un desplegable en la pantalla de login. Decisión explícita del humano (2026-09-25) frente a la alternativa del selector de perfiles.
*   **Integridad:** la unicidad reside en un índice único de PostgreSQL sobre la columna, nunca en una lectura previa (Guard 39).

---

## 📊 Evaluación INVEST

*   **[I]ndependiente:** Sí. Solo depende de `US-010` (alta de personal), ya entregada.
*   **[N]egociable:** El formato exacto del código y su longitud máxima son ajustables; lo que no es negociable es que el identificador de acceso sea visible y tecleable.
*   **[V]aliosa:** Sí. Sin esto, dar de alta a un operario desde la interfaz produce una cuenta a la que nadie puede entrar — el defecto que el humano encontró en uso real.
*   **[E]stimable:** Sí. Una columna con índice único, su migración con relleno, y tres superficies de interfaz.
*   **[S]mall (Pequeña):** Sí. Dos tickets (backend + frontend).
*   **[T]estable:** Sí. Verificable de punta a punta: alta vía API → login con el código devuelto.

---

## 📌 Nota de Alcance

*   **Editar el código de un operario ya creado queda fuera**: la lista lo muestra en modo lectura. Cambiar un identificador de acceso en circulación es una operación distinta (invalida lo que el operario ya memorizó) y merece su propia decisión.
*   **`US-001` Escenario 1 sigue literalmente incumplido** en un punto: describe *«selecciona su perfil»*, y aquí el operario teclea un código. Es una desviación **deliberada y aprobada por el humano** por el NFR de no divulgación — un selector expondría la plantilla completa en una terminal pública sin autenticar. Se documenta como desviación consciente, no como deuda oculta.
