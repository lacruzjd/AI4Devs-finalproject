# 🎟️ TK-173: Código de Operario como Identidad de Acceso, con Unicidad en la Base de Datos (US-051)

> [⬅️ US-051](../../../11_user_stories/auth/US-051.md) | [📖 Índice](../../indice_tickets.md)

## 📝 Descripción

`AUDIT-DEV-017 F-2`: el alta genera `crypto.randomUUID()` como única credencial aceptada por `login-pin`, y ese UUID no se muestra en ninguna superficie. Este ticket introduce `operatorCode` como la identidad con la que el operario entra.

*   **US:** `US-051` · **Slice:** `auth` backend · **SP:** 8 · **Prioridad:** 🟠 P1
*   **Prerrequisitos:** `TK-049` (alta de personal), `TK-056` (listado)

## 🔀 Alcance

*   **Persistencia:** `User.operatorCode String @unique` + migración con relleno (`operatorCode = id` para filas existentes) antes de imponer `NOT NULL` — Escenario 5 de `US-051`.
*   **Dominio:** `UserProps.operatorCode` opcional que **por defecto es el `id`**; `User.operatorCode` getter.
*   **Repositorios:** `IUserRepository.findByOperatorCode()` en `PrismaUserRepository` (insensible a mayúsculas) e `InMemoryUserRepository`.
*   **Aplicación:** `CreateUserUseCase` acepta y devuelve el código; `ListUsersUseCase` lo devuelve; `AuthenticateByPinUseCase` resuelve por código en vez de por id.
*   **HTTP:** `createUserSchema` valida y normaliza (`trim` + `toUpperCase`, `^[A-Z0-9-]{2,12}$`); `loginPinSchema` acepta `operatorCode`; violación del índice único → `409` RFC 7807.
*   **Seed:** `bootstrap-admin` recibe `operatorCode = 'bootstrap-admin'` — las credenciales de revisión publicadas siguen siendo válidas verbatim.
*   **Contrato:** `openapi.yaml` actualizado en los 3 endpoints afectados.
*   **Fuera de alcance:** editar el código de un operario existente (`US-051` Nota de Alcance).

## ✅ Criterios de Aceptación & DoD

1. **TDD (Red primero):** alta con código → login con ese código; código duplicado → `409` desde la restricción real (no desde un `findBy` previo); normalización de caja y espacios; login insensible a mayúsculas; formato inválido → `400`; usuario preexistente sin código conserva acceso por su id.
2. **Paridad de migración:** `check_migration_schema_parity.sh` verde; migración aplicada y verificada contra PostgreSQL real, no solo `prisma validate`.
3. **Sin deriva de contrato:** `check_contract_drift.sh` verde entre `openapi.yaml` y los esquemas Zod.
4. `pnpm build` / `test` / `lint` verdes; sin clones nuevos.
5. **Commit:** `feat(auth): identify operators by a short unique code (TK-173)`.

## 📌 Notas de implementación

*   **Por qué el dominio permite omitir el código y la API no:** el valor por defecto (`operatorCode = id`) existe para una sola cosa — la ruta heredada que la migración rellena y las decenas de tests que construyen `new User({...})` sin conocer este campo. La regla de producto («el administrador lo escribe») vive donde entra el dato real: el esquema Zod del endpoint, que lo exige. Defenderla en dos capas habría duplicado la regla sin añadir garantía.
*   **Guard 39 aplicado literalmente:** la comprobación previa de duplicado se mantiene como camino rápido y legible, pero **no es la defensa**: el `409` se emite igualmente traduciendo el `P2002` de Prisma, de modo que dos altas concurrentes con el mismo código no pueden crear ambas la fila.
*   **Insensibilidad a mayúsculas en el login, unicidad sensible en la columna:** la normalización a mayúsculas en la escritura hace que ambas coincidan en la práctica — no hay dos filas que difieran solo en la caja porque ninguna se persiste en minúsculas.
