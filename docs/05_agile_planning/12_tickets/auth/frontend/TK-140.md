# 🎟️ TK-140: Migrar el token de sesión de `localStorage` a cookie `httpOnly`

> [📖 Índice](../../tickets_index.md) | [⬅️ ADR-005](../../../../02_architecture_design/adr/ADR-005-session-token-storage.md)

## 📝 Descripción

**Remediación técnica** (carve-out C-DEV-006-4) que ejecuta la decisión de [`ADR-005`](../../../../02_architecture_design/adr/ADR-005-session-token-storage.md), confirmada por el humano el 2026-09-09.

Hoy el token viaja y se guarda accesible a JavaScript:

| Punto | Archivo |
| :--- | :--- |
| `localStorage.setItem('restostock_jwt_token', …)` | `apps/frontend/src/features/auth/services/auth.service.ts:29`, `:93` |
| `headers.Authorization = \`Bearer ${token}\`` | `apps/frontend/src/shared/http/apiClient.ts:102` |
| Emisión del token en el cuerpo de la respuesta | `apps/backend/src/application/auth/use-cases/AuthenticateByPinUseCase.ts:71-72` |
| Lectura desde la cabecera `Authorization` | `apps/backend/src/infrastructure/http/middlewares/authenticateJWT.ts:39` |

La fuerza decisiva del ADR: `nginx` ya sirve SPA y API **en el mismo origen** (`location /api/` → `proxy_pass http://backend:3000`), así que la cookie `httpOnly` no arrastra la fricción de CORS que normalmente empuja a las SPAs hacia `localStorage`.

## 🔀 Alcance

**Backend**
- `login-pin` emite el token en `Set-Cookie` con `httpOnly`, `Secure` (condicionado a producción), `SameSite=Strict`, `Path=/api`, `Max-Age` alineado con `expiresIn`.
- `authenticateJWT` lee la cookie; **se mantiene la lectura de `Authorization: Bearer` durante una ventana de compatibilidad** para no invalidar sesiones vivas en el despliegue, con fecha de retirada declarada.
- Endpoint de logout que limpia la cookie server-side.
- Protección **CSRF explícita** para mutaciones — `SameSite=Strict` reduce el vector pero no se asume suficiente (consecuencia negativa registrada en el ADR).

**Frontend**
- `auth.service.ts`: eliminar `localStorage` del token (el `USER_KEY` no sensible puede permanecer o migrar a estado en memoria — decidir en implementación).
- `apiClient.ts`: `credentials: 'include'` y retirada de la cabecera `Authorization`.
- Actualizar `auth.service.test.ts` (hoy asserta `localStorage.getItem('restostock_jwt_token')`).

## ✅ Criterios de Aceptación & DoD

1. Tras un login real, `document.cookie` **no** expone el token y `localStorage` no lo contiene.
2. El flujo completo (login → operación autenticada → idle logout → logout explícito) verificado **contra el stack Docker real**, no solo con tests — [`08_live_stack_verification_workflow.md`](../../../../../.agents/workflows/08_live_stack_verification_workflow.md) (`rules/04_verified_implementation_standard.md`, Antipatrón B).
3. Una mutación sin token CSRF válido es rechazada.
4. `Secure` activo en producción; verificado que la cookie no viaja por HTTP plano.
5. Suites backend y frontend verdes; `ci_local.sh` 3 jobs verdes.
6. `ADR-005` pasa a tener `Implementado por:` con este ticket en `done`.
7. **Commit:** `feat(auth): move session token to httpOnly cookie (TK-140)`.

## 📌 Notas

*   **Post-entrega, por decisión explícita del humano.** Cambia el contrato de autenticación de punta a punta; hacerlo la víspera de la primera corrida real de CI sería temerario.
*   Mientras tanto la exposición está acotada y medida: 0 usos de `dangerouslySetInnerHTML`/`innerHTML` en el frontend, `useIdleTimeout` realmente wireado (`useSession.ts:45`), y [`TK-141`](../../shared/frontend/TK-141.md) añade CSP al `nginx` del SPA antes del push.
*   Este ticket **no** aborda `expiresIn: '12h'` hardcodeado ni el pinneo de algoritmo en `jwt.verify` — hallazgos hermanos de `AUDIT-SEC-004` `O-1`, fuera del alcance declarado del ADR.

## ✅ Resolución (2026-09-30)

### Decisiones de implementación

| Punto | Decisión | Por qué |
| :-- | :-- | :-- |
| CSRF | Token CSRF = HMAC-SHA256 del token de sesión (`csrfTokenFor`), entregado en la cookie legible `restostock_csrf` y exigido en `X-CSRF-Token` en toda petición no GET/HEAD/OPTIONS autenticada por cookie → `403 CsrfTokenMismatchException` | Queda ligado a la sesión sin estado en el servidor; quien no puede leer la cookie `httpOnly` no puede calcularlo. Más fuerte que un double-submit con valor aleatorio independiente. |
| Cuerpo de `login-pin` | Deja de traer `accessToken`; trae `user.permissions` | El SPA ya no puede decodificar el JWT. OpenAPI 9.0.0 (breaking deliberado, confirmado por `oasdiff`). |
| `Max-Age` | Constante compartida `SESSION_TTL_SECONDS` (12 h) para el `expiresIn` del JWT y la cookie | Alineación exigida por el ticket, sin tocar el valor (fuera de alcance según ADR-005). |
| Ventana de compatibilidad | **Backend:** `Authorization: Bearer` se sigue aceptando, sin CSRF, para clientes que no son navegador (tests, scripts, el futuro cliente nativo que ADR-005 anticipa). **Frontend:** lee el token heredado de `localStorage` solo para no expulsar a las sesiones abiertas antes del despliegue; ningún login nuevo lo escribe y el primero lo borra. Retirada de la rama del frontend: [`TK-176`](TK-176.md), a partir del 2026-10-14 | La cabecera `Authorization` no la añade el navegador por su cuenta, así que aceptarla no reabre el vector que cierra este ticket. |
| Logout | `POST /api/v1/auth/logout` sin autenticación, idempotente, 204 | Un script no puede borrar una cookie `httpOnly`. `AuthService.logout()` lo llama con `keepalive` sin esperar, así que el cierre por inactividad usa el mismo camino que el explícito. |

### Verificación contra el stack Docker real (`docker compose up --build`, origen nginx `:8085`)

| Criterio | Evidencia |
| :-- | :-- |
| 1. Token invisible a JS | Chromium (Playwright): cookie `restostock_session` `httpOnly: true`, `secure: true`, `SameSite: Strict`, `Path: /api`; el valor no aparece en `document.cookie` ni en `localStorage`; no existe la clave `restostock_jwt_token`. |
| 2. Flujo completo | Login por la UI → operación autenticada → recarga en `/bodega` conserva sesión → logout explícito (`204`, 0 cookies, API `401`). `change-pin` desde el navegador: `403` sin CSRF, `200` con CSRF. **El cierre por inactividad no se esperó (15 min):** comparte `logout()` con el cierre explícito, que sí se verificó. |
| 3. Mutación sin CSRF rechazada | `403 CsrfTokenMismatchException` desde el navegador y desde curl. |
| 4. `Secure` en producción | `Set-Cookie ... HttpOnly; Secure; SameSite=Strict`. Por HTTP plano desde la IP de la LAN (`http://192.168.x.x:8085`) el cliente **no guarda** la cookie y la siguiente petición es `401`. |
| 5. Suites y CI local | Backend 638, frontend 307 en verde; `ci_local.sh` completo con `exit 0` (2026-09-30). |

**Consecuencia operativa (la acepta ADR-005, se hace visible aquí):** con `NODE_ENV=production`, una tablet que abra el stack por `http://<IP-LAN>` inicia sesión (`200`) pero el navegador descarta la cookie `Secure`, así que la siguiente petición vuelve al login. `localhost` funciona porque los navegadores lo tratan como contexto seguro. Para uso en LAN hace falta HTTPS delante de nginx.

**Datos de verificación que quedan en la BD local del stack Docker:** rol `QA_BODEGA_TK073` y operarios `QA-TK140` / `QA-TK073`, ambos **bloqueados**.
