## Descripción

**Remediación técnica** (Guard 26, carve-out C-DEV-006-4) de los hallazgos **F-1** y **F-2** de [`AUDIT-DEV-016`](../../../../audits/AUDIT-DEV-016-momoy-naming-consistency.md).

El prefijo `NN_` significa cinco cosas distintas en `.agents/` según el directorio, y la correlación es exacta con lo que `CONTRIBUTING.md` documenta: **todo lo documentado se respeta; todo lo que ha derivado es justo lo que ese fichero no cubre**. No hay sección para añadir una rule, un example ni un script. El `NN_` de `rules/` no codifica orden ni prioridad — es la fecha de alta disfrazada (`00`→15-ago … `05`→22-ago, verificado con `git log --diff-filter=A`).

Este ticket **no renombra nada**: escribe el estándar que `TK-151` verificará y hará cumplir. Se hace primero para que los renombrados se justifiquen contra una regla publicada, no contra el criterio del agente del momento.

## Alcance del contenido a escribir

1. **Principio rector**, como regla permanente con su propia sección:
   > El prefijo numérico sólo se usa cuando codifica **orden de ejecución** o **espejo de una taxonomía externa**. En todo lo demás el nombre manda, y el número es un **ID estable**, nunca una posición.
2. **Sección "Añadir o modificar una Rule"** — nombre descriptivo con sufijo `_standard.md`, **sin prefijo numérico** (no hay orden de lectura que justificarlo), y registro en `rules/README.md`.
3. **Sección "Añadir un Example"** — numeración **local a su subcarpeta** (`backend/01_`, `frontend/01_`), sufijo `.example.md` obligatorio también en la raíz.
4. **Sección "Añadir un Script"** — prefijo `check_` obligatorio para todo validador que `validate_agents.sh` invoque; sin prefijo para el tooling de instalación/sincronización; un único lenguaje por familia.
5. **Aclaración explícita** de que el `NN_` de la carpeta (`skills/development/05_quality_and_lint/`) y el `SK-NN` del fichero (`SK-19_…`) son **independientes por diseño** y nunca correlacionarán: el primero agrupa por fase, el segundo es un ID cronológico global estable.
6. **Criterio de ubicación para skills de pruebas** (F-2): resolver el solape entre `05_quality_and_lint` y `08_testing` declarando cuál recibe una skill de pruebas nueva, sin mover ninguna skill existente.

Todo el texto respeta la política sin emojis decorativos (`check_emoji_policy.py`) y el agnosticismo (`check_agnosticism.py --strict-docs`): ningún ejemplo puede citar identificadores, rutas ni stack de este proyecto.

## Mitigación de Riesgos Técnicos
1. **Escribir un estándar que el árbol actual ya viola sin decirlo:** cada regla nueva declara explícitamente qué ficheros del árbol actual la incumplen y remite a `TK-151`, para que nadie lea `CONTRIBUTING.md` como descripción del estado real cuando todavía es el estado objetivo.
2. **Acoplar la documentación al proyecto consumidor:** las secciones nuevas no citan `RestoStock`, ni rutas de este monorepo, ni tickets reales. `check_agnosticism.py --strict-docs` es bloqueante y lo verifica.
3. **Regla inverificable:** ninguna regla se escribe si `TK-151` no puede comprobarla mecánicamente; si una idea no es verificable, se descarta en vez de quedar como prosa aspiracional.
