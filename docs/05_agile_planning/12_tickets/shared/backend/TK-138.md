# 🎟️ TK-138: Hacer real el gate de mutación en CI (diff-scoped) + config de Stryker en frontend

> [📖 Índice](../../indice_tickets.md)

## 📝 Descripción

**Remediación técnica** (carve-out C-DEV-006-4). `docs/00_stack_manifest.md` §5 declara «Mutation Score ≥ 70 %» pero la auditoría de preparación para producción (2026-09-06) mostró que ese umbral **no se hace cumplir en CI**:

| # | Situación al 2026-09-09 | |
| :- | :- | :- |
| 1 | El paso de CI `Mutation Testing — Domain & Application` corre `pnpm --filter @restostock/backend run test:mutation`, que mutila **todo** `src/domain/**` + `src/application/**` (cientos de archivos, muchas horas) con `continue-on-error: true` → nunca termina, nunca bloquea, solo quema minutos de runner. | ⚠️ |
| 2 | `docs/04_governance_and_quality/scripts/check_mutation_score.sh` **sí** es correcto (una invocación de Stryker por archivo, `thresholds.break` por archivo) pero está diseñado para uso **local pre-commit**: calcula los archivos vía `git diff` contra el *working tree* / *staged* / *untracked*. En un checkout de CI no hay cambios sin commitear → no muta nada. | ⚠️ |
| 3 | `apps/frontend` **no tiene configuración de Stryker en absoluto**. | ⚠️ |
| 4 | El runner Stryker+Vitest **ya funciona** (corrida del 2026-09-09: *"Ran 32.90 tests per mutant on average"*, frente al *"0.00"* del 2026-09-06 — se arregló en algún punto entre ambas fechas). El problema que queda es de **wiring**, no de runner roto. | ✅ |

`TK-137` ya cerró el hallazgo colateral (`Temperature.ts` sin test directo).

## 🔀 Alcance propuesto

1. **`check_mutation_score.sh`**: aceptar un ref base opcional (`$1`). Con ref → `git diff --name-only "$BASE"...HEAD`; sin ref → comportamiento actual (working tree). Una sola fuente de verdad para local y CI (Guard 27: los checks viven en `docs/04_governance_and_quality/scripts/`, no inline en el workflow).
2. **`.github/workflows/ci.yml`**: sustituir el paso `test:mutation` full-scope por `bash docs/04_governance_and_quality/scripts/check_mutation_score.sh <base-sha>`. Mantener `continue-on-error: true` en esta entrega (informativo) — la promoción a **bloqueante** es una decisión aparte una vez se confirme que la corrida diff-scoped cabe en el tiempo de CI.
3. **`apps/frontend/stryker.conf.json`** (nuevo) + `test:mutation` en `apps/frontend/package.json`, y extender `check_mutation_score.sh` (o un `check_mutation_score_frontend.sh`) para `apps/frontend/src/{domain,application,shared}` según la arquitectura real del front.
4. **`docs/00_stack_manifest.md` §5**: reescribir la nota de verificación para que refleje el estado final (gate diff-scoped real, alcance por archivo, informativo vs bloqueante).

## ✅ Criterios de Aceptación & DoD

1. En un PR que toque un archivo `apps/backend/src/domain/**`, el paso de CI corre Stryker **solo** sobre ese archivo y publica su score en el log del job.
2. Un PR que no toque `domain/`/`application/` → el paso sale verde sin correr Stryker.
3. `apps/frontend` tiene `stryker.conf.json` y una corrida diff-scoped equivalente.
4. `ci_local.sh` sigue verde; `check_mutation_score.sh` sin ref se comporta igual que hoy (sin regresión para el flujo local de `02_cascading_dev_workflow.md`).
5. Manifest §5 actualizado.

### El punto 3 cambió por una medición, no por opinión

El humano decidió incluir el frontend. Al **ejecutarlo de verdad** apareció el dato que no teníamos al decidir:

```
errorMessageMapper.ts (1 fichero)
  10 min 42 s   (backend: 2:42 — ~4×)
  score 64.04 % (por debajo del umbral de 70)
  9.47 tests por mutante (backend: 32.9–123.9)
  24 de 89 mutantes son TIMEOUTS
```

Los timeouts son lo decisivo: Stryker los cuenta como "detectados", así que **buena parte de ese 64 % no son tests que atrapan el defecto** — es exactamente el patrón que invalidó la medición del backend el 2026-09-06. Un PR con 3 ficheros de front sumaría ~32 min de runner para producir un número que sabemos inflado.

**Resolución:** la config se conserva (`apps/frontend/stryker.conf.json`, útil para análisis manual) pero el gate automático es **backend-only**; el frontend entra sólo con `--with-frontend`. La justificación medida está escrita en los tres sitios: el script, la config y el manifiesto.

### Fallo encontrado al implementar

El Job 3 hacía checkout **shallow** (`fetch-depth` por defecto; sólo el Job 2 tenía `0`). Con eso `git diff <base>...HEAD` no encuentra el ref y **el gate habría salido verde sin mutar un solo archivo** — un Gate Hueco creado por este mismo ticket. Añadido `fetch-depth: 0`.

También cambió `pnpm-lock.yaml` al añadir las dependencias de Stryker al frontend; sin commitearlo, `pnpm install --frozen-lockfile` rompe el Job 1 en su primer paso. Verificado con el mismo comando que usa CI.
